The throughline: let the machine do what the machine is good at. The compiler is deterministic, fast and tireless. An agent is not.

The problem with “fast”

  • Agents duplicate boilerplate in seconds
  • Copy-paste at scale → drift, inconsistency, subtle bugs
  • 10 variants of “almost the same” → maintenance hell
  • More code = more surface for mistakes

AI makes it cheap to do the wrong things — at scale.

The temptation is strong: "the agent does it in a second anyway." But ten duplicated converters are ten places that can drift out of sync.

Part two

Analyzers

Let the compiler enforce your rules

Part 2. This is the emotional core of the talk.

Instructions vs. enforcement

  • Conventions in a README, CLAUDE.md or copilot-instructions
  • … get read when it's convenient
  • An agent can ignore, forget or “creatively interpret” an instruction

AI agents can ignore instructions.
Build errors, they can't.

This is the core of part 2. A prompt is a suggestion. An analyzer error is a hard wall. The agent can only move on once the code compiles.

The code fix (APP1001)

Code fixes need Microsoft.CodeAnalysis.Workspaces — which the analyzer must not reference.

Per the Microsoft docs, RegisterCodeFixesAsync lives in Microsoft.CodeAnalysis.Workspaces.dll. That's why the fix belongs in its own assembly: put it next to the analyzer and the Workspaces reference trips RS1038. I will NOT walk the API line by line here — an agent does that trivially.

Analyzer 2 — an architecture rule

A team agreement becomes a build error — no more review discussion needed.

This is a real architecture rule: don't inject a DbContext, inject a factory (concurrency, lifetime). You used to catch this in code review. Now the compiler catches it — before the PR, for the agent too. Foreshadow part 3: this one is written in the SLOW style. We'll come back to it.

Part three

Performance

The warning your agent doesn't feel

Part 3. The part nobody warns you about.

Why performance is critical

  • Analyzers are injected into every project
  • They run on every build — and continuously in the IDE
  • A slow analyzer runs on every keystroke, across the whole solution

One sloppy analyzer taxes the IDE responsiveness and the build time of the entire team.

This is the hidden cost. Functionally a slow analyzer works perfectly — it doesn't "fail". But it eats away at everyone's developer experience, every day.

Slow vs. fast

Two mistakes: scope-checking inside the per-node action, and ToDisplayString() per node.

The two biggest mistakes: (1) scope-check inside the per-node action instead of once per compilation, and (2) ToDisplayString() per node, which allocates a string every time. Resolve markers once, compare by symbol. Next slide quantifies it — that's the one that makes people sit up.

Example

The shipped analyzer in examples/. Three things to point at: scope gate, resolve-once, and the closure instead of a field (RS1008 forbids per-compilation state in analyzer fields, because one analyzer instance serves many compilations).

One keystroke, whole solution

✗ SLOW ToDisplayString() per nodeno scope gate — visits every project
nodes visited 0 strings allocated 0 elapsed 0 ms
✓ FAST scope gate + symbol compareirrelevant projects do zero work
nodes visited 0 strings allocated 0 elapsed 0 ms
40 projects · 12 000 symbols · 1 keystroke
Illustrative simulation, not a benchmark — be honest about that if asked. The shape is what's real: the slow analyzer visits every symbol in every project and allocates a string each time; the fast one skips 37 of 40 projects entirely at compilation-start and never allocates. Then say the line: the agent cannot feel this. It only sees "compiles / doesn't compile".

The checklist for fast analyzers

  • Scope once in RegisterCompilationStartAction — irrelevant projects do 0 work
  • Resolve marker types once via GetTypeByMetadataName, compare with SymbolEqualityComparer
  • Never ISymbol.ToDisplayString() per node — it allocates every time
  • EnableConcurrentExecution() + ConfigureGeneratedCodeAnalysis(None)
These are the rules you bake into a skill, so your agent follows them every time.

Generators must be fast too

  • Use IIncrementalGenerator — not the old ISourceGenerator
  • ForAttributeWithMetadataName → the pipeline only runs on relevant nodes
  • Model as an equatable record struct → the compiler caches and doesn't regenerate needlessly
  • Keep the transform step pure and small

A non-incremental generator re-runs on every keystroke → IDE lag.

Incremental is the key. The equatable data model (readonly record struct) lets the pipeline cache results and only recompute what actually changed.

Make your agent aware of this

What an agent sees

compiles / doesn't compile

It doesn't feel IDE lag. It never waits for its own analyzer. Without direction it writes a correct but slow one — and nothing tells it.

What you must add

performance as an explicit review item

Not an afterthought, not a code-review reflex you hope someone has. Written down, in the repo, loaded automatically.

The agent optimizes for what you hold it accountable to. Hold it accountable for performance.

This is exactly why we need a skill: give the performance knowledge to the agent structurally, instead of hoping it knows.
